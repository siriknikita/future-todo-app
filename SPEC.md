Future Todo 

 

1. Сфера застосування продукту 

Future Todo є кросплатформним застосунком для планування особистих і спільних задач із синхронізацією між пристроями. 

До складу продукту входять: клієнтські застосунки для Web, Windows, macOS, Linux, Android та iOS; серверна частина, що забезпечує зберігання даних, синхронізацію, спільний доступ і сповіщення. 

Продукт розробляється у два архітектурні етапи. Спочатку створюється монолітна серверна частина, потім вона рефакториться до мікросервісної архітектури. 

 

2. Перспектива продукту 

Future Todo є новим самостійним продуктом із клієнт-серверною архітектурою. Кожен клієнт зберігає локальну копію даних користувача й обмінюється змінами із сервером через API. Сервер відповідає за постійне зберігання, синхронізацію між пристроями, спільний доступ і надсилання сповіщень. 

 

3. Функції продукту 

Продукт має забезпечувати: 

керування обліковим записом; 

створення списків і груп списків; 

керування задачами (терміни, нагадування, повторення, кроки, нотатки, вкладення); 

розумні списки та план «Мій день» із пропозиціями; 

спільний доступ до списків і призначення задач; 

пошук, сортування та фільтрацію; 

персоналізацію інтерфейсу; 

синхронізацію між пристроями й роботу без мережі; 

функції, специфічні для платформ (віджети, гарячі клавіші, системні сповіщення).

5. Припущення та залежності  

Для синхронізації потрібне підключення до Інтернету; без мережі клієнт працює з локальними даними. 

Продукт залежить від сторонніх сервісів: Apple Push Notification service і Firebase Cloud Messaging (push-сповіщення), OAuth-провайдерів Google, Apple, Microsoft (вхід), поштового сервісу SMTP, S3-сумісного сховища файлів. 

Передбачається, що користувач дає дозвіл на сповіщення в операційній системі 

 

6. Етапи реалізації вимог 

Етап 1. Монолітна архітектура. Уся серверна функціональність реалізується в одному застосунку з однією базою даних. Код поділяється на модулі з чіткими межами (облікові записи, задачі та списки, спільний доступ, сповіщення, синхронізація, файли). Це дозволить надалі без значних змін виділити кожен модуль в окремий сервіс. 

Етап 2. Мікросервісна архітектура. Модулі поступово виділяються в окремі сервіси за патерном Strangler Fig: Identity Service (Реєстрація, автентифікація, OAuth, керування сесіями), Task Service (Списки, групи, задачі, кроки, розумні списки), Sharing Service (Запрошення, учасники, права доступу, призначення задач), Sync Service (Черги змін, розв'язання конфліктів, real-time розсилка змін), Notification Service (Планування та доставка нагадувань (push, email)), File Service (Завантаження, зберігання та видача вкладень), Search Service (Повнотекстова індексація та пошук) API Gateway	(Маршрутизація, автентифікація запитів, обмеження частоти). 

Перехід на етап 2 не повинен змінювати зовнішній API для клієнтів. Клієнтські застосунки не потребують оновлення через зміну серверної архітектури. 

 

7. Вимоги до зовнішніх інтерфейсів 

Інтерфейс має єдину структуру на всіх платформах: бічна панель списків, основна область задач і панель деталей задачі. При цьому він адаптується до конвенцій кожної платформи. Також мають бути забезпечені: 

світла й темна теми; 

жести на мобільних пристроях (свайп для виконання або видалення задачі); 

гарячі клавіші на десктопі; 

відповідність WCAG 2.1 рівня AA; 

локалізація українською та англійською мовами. 

Програмні інтерфейси. 

API операційних систем для сповіщень, віджетів і фонової синхронізації. 

APNs і FCM для push-сповіщень. 

OAuth 2.0 / OpenID Connect для входу через Google, Apple, Microsoft. 

SMTP для службових листів. 

S3-сумісне API для зберігання файлів. 

Реляційна СКБД для постійного зберігання даних. 

Комунікаційні інтерфейси. 

Обмін даними клієнта із сервером відбувається виключно через HTTPS (TLS 1.2 або вище). 

API побудовано за принципами REST з форматом JSON і описано в специфікації OpenAPI 3. 

Для передачі змін у реальному часі використовується WebSocket. 

На етапі 2 сервіси взаємодіють між собою через брокер повідомлень

9. Обмеження проєктування 

Клієнтські застосунки розробляються на єдиній кодовій базі за допомогою кросплатформного фреймворку (наприклад, Flutter) з платформними модулями для віджетів і сповіщень. 

API версіонується, і зворотна сумісність зберігається щонайменше для однієї попередньої версії. 

На етапі 1 модулі моноліту не мають прямого доступу до таблиць інших модулів, а взаємодіють лише через внутрішні інтерфейси. 

На етапі 2 кожен сервіс має власну базу даних, упаковується в контейнер і розгортається незалежно. 

Відповідно до практик XP розробка ведеться через тестування (TDD), покриття коду автотестами становить не менше 80%, а кожна зміна проходить автоматичну збірку й тести в CI. 

Команда дотримується єдиного стандарту кодування, що перевіряється автоматичними лінтерами. 

 

10. Атрибути якості системи 

Система повинна забезпечувати високий рівень надійності, безпеки, зручності використання, супроводжуваності, переносимості та масштабованості. Доступність серверної частини повинна становити не менше 99,9 % на рік, резервне копіювання даних має виконуватися щодня, при цьому допустима втрата даних (RPO) не повинна перевищувати 1 години, а час відновлення системи (RTO) - 4 годин. Для забезпечення безпеки паролі повинні зберігатися із використанням алгоритмів Argon2 або bcrypt, access-токени JWT повинні мати термін дії 15 хвилин із подальшим оновленням за допомогою refresh-токенів, а частота запитів повинна обмежуватися для захисту від атак перебором паролів. Дані, що зберігаються в системі, повинні бути зашифровані, а програмне забезпечення - захищене від основних вразливостей, визначених OWASP Top 10; кожен користувач повинен мати доступ лише до власних даних і даних, до яких йому надано спільний доступ. Система повинна бути зручною у використанні: створення нової задачі з головного екрана має виконуватися не більше ніж за дві дії, а новий користувач повинен мати можливість освоїти основні функції без спеціального навчання. Для забезпечення супроводжуваності програмний код повинен мати модульну структуру та бути покритий тестами, API має бути задокументовано відповідно до OpenAPI, а для кожного сервісу повинна вестися технічна документація. Система повинна бути переносимою, тобто забезпечувати однакову основну функціональність на всіх цільових платформах, за винятком функцій, специфічних для окремих платформ. На другому етапі розвитку кожен сервіс повинен мати можливість незалежного горизонтального масштабування. Крім того, продукт повинен відповідати юридичним вимогам, зокрема містити політику конфіденційності та умови використання, забезпечувати права користувачів на доступ, експорт і видалення персональних даних відповідно до вимог GDPR, а також відповідати правилам App Store і Google Play. Формати дат і часу повинні визначатися відповідно до регіональних налаштувань користувача, а всі нагадування мають враховувати його поточний часовий пояс. 

 

11. Особливості проєкту, що визначають вибір методології 

По-перше, продукт одночасно випускається на шести платформах (Web, Windows, macOS, Linux, Android, iOS). Тому ризик несумісностей і помилок інтеграції дуже високий, а виявляти їх потрібно якомога раніше. 

По-друге, архітектура продукту змінюється в ході розробки: серверна частина спочатку створюється як моноліт, а потім рефакториться до мікросервісів. Отже, методологія має забезпечувати безпечну зміну вже працюючого коду. 

По-третє, загальний набір функцій відомий заздалегідь, оскільки орієнтиром є Microsoft To Do. Проте деталі поведінки, пріоритети та зручність інтерфейсу на кожній платформі уточнюватимуться лише після того, як замовник і користувачі побачать працюючий продукт. 

Екстремальне програмування найкраще відповідає цим умовам, оскільки основні ризики проєкту технічні, а XP, на відміну від більшості гнучких методологій, містить конкретні інженерні практики для роботи саме з такими ризиками, а саме рефайторин, TDD, парне програмування.  

Перехід від моноліту до мікросервісів є масштабним рефакторингом. В XP рефакторинг - це не окремий етап, а постійна щоденна практика. Команда звикає змінювати структуру коду без зміни його поведінки, тому розділення на сервіси відбувається поступово (за патерном Strangler Fig), без зупинки розробки нової функціональності. Тести, написані на етапі моноліту, стають «страховкою» під час міграції: той самий набір тестів перевіряє, що після виділення сервісу поведінка системи не змінилася. Особливо це важливо для вимоги про незмінність зовнішнього API для клієнтів, яку перевіряють приймальні тести на рівні API. 

Принцип XP «роби найпростіше рішення, яке працює» прямо обґрунтовує старт із моноліту. Будувати мікросервіси з першого дня означало б ускладнювати систему до того, як з'явилася реальна потреба в масштабуванні (PR-4). Моноліт дає змогу швидко випустити робочий продукт, а мікросервіси запроваджуються тоді, коли межі модулів стабілізувалися й навантаження зросло. Шість клієнтських платформ і серверна частина мають збиратися й тестуватися після кожної зміни. Інакше помилки, специфічні для платформ, накопичуватимуться й виявлятимуться лише перед релізом. На етапі мікросервісів CI/CD також забезпечує незалежне розгортання кожного сервісу.
